================================================================================
Person 3 — Frontend (React / Vite) — READ THIS TO UNBLOCK
================================================================================

Branch idea: frontend-ui

Environment:
  • Copy frontend/.env.example → frontend/.env
  • VITE_API_BASE_URL=http://localhost:5000   (dev)
  • In production: VITE_API_BASE_URL=https://<your-deployed-node-host>

Auth flow (do this first in the app):
  1) POST ${VITE_API_BASE_URL}/api/v1/auth/login
     Body: { "email", "password" }
     Response: data.session.access_token, data.profile.role, data.user
  2) Store access_token (memory + sessionStorage is OK for demo; production may differ).
  3) Every API call: headers: { Authorization: `Bearer ${access_token}` }

Role-based routing (read data.profile.role after login):
  • worker
  • verifier
  • advocate

What each role should SEE and DO in the UI (map to APIs):

--- WORKER ---
  SEE: Own shift logs, own certificate, city benchmark for own city_zone, grievance list (own).
  DO:
    • Log shift — POST .../api/v1/earnings/shift-logs  (body: current_shift fields per OpenAPI/Python model)
    • CSV import — POST .../api/v1/earnings/shift-logs/import-csv  (multipart file)
    • Anomaly check — POST .../api/v1/anomaly/analyze  (current_shift + optional history)
    • My pay vs median — GET .../api/analytics/benchmarks/platform-city?platform=...&city_zone=...
      (city_zone must match profile.city_zone)
    • Certificate — GET .../api/certificates/workers/<your-user-id>/verified-logs
      (workerId must be your auth user id)
    • Grievances — GET/POST .../api/grievances  (POST body worker_id ignored; server uses JWT)

--- VERIFIER ---
  SEE: Pending shift logs (use earnings list with status=pending or filter in UI), grievances broadly.
  DO:
    • List logs — GET .../api/v1/earnings/shift-logs?worker_id=...&status=pending  (optional filters)
    • Approve/flag — PATCH .../api/v1/earnings/shift-logs/{id}/verification
    • Vulnerability dashboard — GET .../api/analytics/vulnerability-flags?threshold=20
    • Optional sanity check — GET .../api/v1/verifier/ping

--- ADVOCATE ---
  SEE: Same wide analytics as verifier; grievances across workers.
  DO:
    • GET .../api/analytics/vulnerability-flags
    • GET .../api/grievances  (optional query worker_id, filters)
    • Benchmarks for any city — GET .../api/analytics/benchmarks/platform-city?...  (no worker city lock)
    • Certificates for any worker — GET .../api/certificates/workers/{workerId}/verified-logs

Mock data: Optional for layout-only screens. For demo with judges, prefer real API
calls above once Node + Supabase are up.

Full API detail: service-grievance-node/docs/openapi.yaml + Python /docs for
earnings/anomaly request bodies.
